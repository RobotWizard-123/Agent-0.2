# 机房管理 Agent V0.2 演示版设计规格

日期：2026-07-21  
状态：设计已确认，待用户审阅规格文档

## 1. 目标

在现有无外部依赖的 Node.js MVP 上构建一个可远程访问、可供领导现场操作的机房管理 Agent 演示网站。系统围绕设备上架、容量管理、链路查询、设备变更和报警诊断形成完整交互闭环，并保留一次最终确认。

V0.2 使用 JSON 保存演示状态，通过接口边界预留 NetBox、PDU、配电支路和网络设备采集能力。当前阶段不迁移到 NetBox，也不执行真实物理操作。

## 2. 设计原则

- 确定性规则引擎负责事实计算和硬约束，语言模型不得绕过硬约束。
- Agent 可以调整候选机柜、层位、隔板位置、设备顺序和软约束取舍，但调整后必须重新校验。
- 所有改变系统状态的方案只保留一次最终确认；只读查询不需要确认。
- 所有演示场景必须可触发、可诊断或规划、可确认、可执行、可验证、可追溯。
- 演示数据、规则计算结果和未来实时采集数据必须有清晰的数据来源标签。
- 缺失数据必须显示为未知或未接入，不得按零值处理，也不得推测不存在的链路。

## 3. V0.2 范围

### 3.1 包含

- 机房总览和容量态势。
- 22 个机柜的平面可视化。
- 42U 机柜、四层结构、隔板和具体服务器信息可视化。
- 自然语言或结构化表单发起单台/批量上架任务。
- 空间、设计功率、重量和端口等约束判断。
- Agent 推荐、调整、解释和确定性复核。
- 设备迁移、隔板调整等模拟变更。
- 电力与网络链路查询。
- 报警产生、Agent 诊断、修复建议、模拟恢复和审计闭环。
- 模拟采集器或模型服务故障及降级处理。
- 统一最终确认、模拟执行、执行验证和变更审计。
- 一键恢复初始演示数据。
- 登录保护和适合服务器部署的容器化入口。

### 3.2 不包含

- NetBox 正式部署和生产数据迁移。
- PDU、配电柜、交换机或监控平台的实时采集。
- 真实远程开关电、交换机配置或工单执行。
- 未经确认的自动物理变更。
- 将图纸中的多个支路展示为未经证实的 A/B 双路冗余。

## 4. 已确认的机房事实与约束

### 4.1 机房和机柜

L5-A2-08 机房共 22 个机柜，其中 20 个服务器机柜、2 个网络/交换机机柜。

| 机柜 | 类型 | 设计容量 | 配电来源 | 断路器 | 电缆 |
| --- | --- | ---: | --- | --- | --- |
| CAB-01～CAB-08 | 服务器 | 10 kW | JG1 | C40/2P | 3×10 |
| CAB-09～CAB-10 | 服务器 | 20 kW | JG1 | C63/2P | 3×16 |
| CAB-11～CAB-13 | 服务器 | 20 kW | JG2 | C63/2P | 3×16 |
| CAB-14～CAB-20 | 服务器 | 10 kW | JG2 | C40/2P | 3×10 |
| CAB-21～CAB-22 | 网络/交换机 | 5 kW | KT1 | C40/2P | 3×10 |

JG1 图纸计算负荷为 96 kW，JG2 为 104 kW。服务器机柜当前仅按 10/20 kW 设计上限计算；未来接入真实功率后，同时展示实时值和设计上限，设计上限仍是不可突破的硬约束。

### 4.2 机柜分层

- 所有机柜统一为 42U。
- 三块隔板形成 L01、L02、L03、L04 四层。
- L01 固定为 U01～U12，第一块隔板固定在 U12。
- 其余两块隔板可移动，保存为 `[12, x, y]`，并由 Agent 推荐位置。
- L02、L03、L04 合计占用剩余 30U。
- 每一层整体预留 2U，而不是每台服务器预留 2U。
- 10U 服务器必须位于底层 L01。
- 高 U 设备优先放低层，同层内较大设备在下、较小设备在上。
- Agent 可以在容量紧张时提出跨机柜迁移现有服务器或调整隔板，但该方案必须显示风险并重新校验。

### 4.3 规则边界

硬约束包括 42U、L01 固定 12U、每层 2U 预留、设计功率上限、机柜重量上限、网络端口容量、设备尺寸和设备类型限制。任何硬约束失败都必须阻止进入最终确认。

软约束包括优先机柜、相邻性、业务分散、容量利用率、迁移数量和布线便利度。Agent 可调整软约束取舍，但必须展示调整前后结果和原因。

## 5. 总体架构

V0.2 保持单体 Node.js Web 应用，内部按职责拆分，避免演示数据源和未来生产数据源互相耦合。

### 5.1 组件

- `InventoryRepository`：读取和保存房间、机柜、服务器、端口和链路。V0.2 使用 JSON，后续替换为 NetBox API 实现。
- `TelemetryProvider`：提供功率、在线状态和采集时间。V0.2 返回标记明确的模拟值或“未接入”，后续接入 PDU 与监控系统。
- `PlanningEngine`：生成上架、迁移、隔板调整和批量重排候选方案。
- `ConstraintEngine`：执行空间、功率、重量、端口和位置硬约束校验，并输出结构化证据。
- `AgentGateway`：调用兼容 OpenAI Chat Completions 的私有模型，负责需求抽取、方案解释和允许范围内的调整。
- `AlarmEngine`：基于规则、模拟遥测和服务健康事件产生告警，管理告警状态。
- `DiagnosisEngine`：关联库存、容量、拓扑和变更历史，生成根因假设、证据、影响范围和处置建议。
- `ExecutionAdapter`：V0.2 只执行带快照的模拟变更；后续可以增加真实自动化适配器。
- `AuditLog`：保存请求、原方案、Agent 调整、校验结果、确认人、执行结果和恢复结果。
- Web UI/API：提供可视化、交互表单、状态刷新、最终确认和结果跳转。

### 5.2 Agent 调用流程

1. 用户用自然语言或结构化表单提交请求。
2. 模型将自然语言转换成结构化参数。
3. 服务端对参数进行模式和类型校验。
4. `PlanningEngine` 和 `ConstraintEngine` 计算候选方案与风险。
5. Agent 可在授权范围内调整候选方案并解释原因。
6. 调整后的方案再次进入 `ConstraintEngine`。
7. 只有无阻断项的方案才进入一次最终确认。
8. 确认时检查数据版本并锁定相关资源。
9. `ExecutionAdapter` 模拟执行，随后重新读取状态进行验证。
10. UI 更新机柜、容量、拓扑、告警和审计记录。

## 6. 数据模型

### 6.1 核心实体

- `Room`：机房编号、名称、平面图引用、机柜集合。
- `Rack`：编号、类型、42U 高度、设计功率、重量上限、端口上限、配电信息和数据版本。
- `RackLayer`：层号、U 位范围、2U 预留、设备集合和剩余空间。
- `DividerLayout`：三块隔板位置 `[12, x, y]`。
- `Device`：资产编号、主机名、型号、序列号、U 高、额定功率、重量、端口需求、业务、负责人和状态。
- `Placement`：机柜、层、起止 U 位和排序位置。
- `PowerConnection`：配电柜、支路、PDU 和插口；未知字段显式为空。
- `NetworkConnection`：设备端口、交换机、交换机端口、VLAN 和 IP；未知字段显式为空。
- `CapacitySnapshot`：设计功率、额定功率合计、实时功率、空间、重量、端口及采集时间。
- `Plan`：请求、原始方案、Agent 调整、校验证据、风险和状态。
- `Alarm`：来源、级别、对象、触发规则、证据、影响范围和状态。
- `Diagnosis`：根因假设、置信度、证据、建议动作和关联方案。
- `ChangeRecord`：确认、执行、验证、失败恢复和审计信息。

### 6.2 数据来源标签

所有容量与告警值带有 `source`：

- `design`：图纸或配置中的设计事实。
- `rule`：确定性规则计算结果。
- `demo`：明确标记的模拟演示数据。
- `telemetry`：未来真实采集数据。
- `unknown`：尚未接入或缺失。

## 7. 状态流转

### 7.1 方案状态

`draft → planned → validated → awaiting_confirmation → locked → executing → succeeded/failed`

- 数据版本变化时，从 `awaiting_confirmation` 退回 `planned` 并重新计算。
- 硬约束失败时保持在 `planned` 或 `validated`，不得进入确认。
- 执行失败时恢复执行前快照，并形成失败告警和审计记录。

### 7.2 告警状态

`open → acknowledged → diagnosing → action_pending → executing → resolved`

- 无需变更即可恢复的服务健康告警可从 `diagnosing` 直接进入 `resolved`。
- 涉及状态变更的处置方案必须进入一次最终确认。
- 告警恢复必须由规则重新计算或健康检查验证，不能只靠前端按钮改为已恢复。

## 8. 页面与交互

### 8.1 机房总览

- 展示 22 个机柜的平面分布、类型、设计容量、使用率、告警颜色和状态。
- 点击机柜进入机柜详情；点击配电来源进入链路视图；点击告警角标进入告警诊断。
- 容量统计区区分设计功率、额定功率合计、实时功率未接入和风险数量。

### 8.2 机柜与服务器详情

- 以 42U 和四层结构展示隔板、空闲 U 位、每层 2U 预留和服务器位置。
- 服务器详情展示资产编号、主机名、型号、序列号、层/U 位、U 高、额定与实时功率、重量、网络端口、IP/VLAN、PDU 插口、交换机端口、业务、负责人和状态。
- 支持从服务器跳转到电力/网络链路、关联告警和变更历史。

### 8.3 Agent 规划台

- 支持自然语言输入和结构化表单互相切换。
- 展示参数抽取结果、候选方案排名、容量计算、隔板建议、Agent 调整记录和风险。
- 硬约束用红色阻断，需关注风险用黄色提示，可执行方案用绿色标识。
- 模型不可用时保留结构化表单和本地规则规划能力。

### 8.4 最终确认与模拟执行

- 最终确认页展示受影响机柜、服务器、隔板、容量前后对比、告警变化和回退快照。
- 用户只确认一次；执行前服务端再检查数据版本和硬约束。
- 执行过程展示锁定、写入、验证和审计四个阶段，完成后可跳转到更新后的机柜。

### 8.5 拓扑与变更日志

- 支持按服务器、机柜、配电来源或交换机查询。
- 展示 `机房 → 配电柜/支路 → 机柜/PDU → 服务器` 电力链路和 `服务器 → 交换机端口 → 交换机` 网络链路。
- 多个支路只按图纸事实展示，不标记为 A/B 冗余。
- 变更日志可以反向跳转到方案、执行结果、服务器和告警。

### 8.6 报警诊断

- 告警列表展示级别、来源、设备、时间、状态和数据来源。
- 支持设计功率高/超限、空间冲突、重量超限、端口不足、分层冲突、采集器离线、模型服务异常和模拟执行失败。
- 详情展示触发规则、原始数据、影响链路、根因假设、置信度、证据和影响范围。
- 提供“交给 Agent 生成处置方案”，方案可以调整机柜、迁移服务器、调整隔板、暂停上架或建议人工检查采集链路。
- 处置方案重新进入规则校验、最终确认、模拟执行和恢复验证流程。
- 页面明确标记“规则告警”“模拟告警”“未来实时采集”。

## 9. 可交互闭环场景

### 9.1 设备上架

提交设备需求，查看 Agent 推荐与风险，确认模拟执行，观察机柜位置和容量变化，并在变更日志中查看全过程。

### 9.2 容量不足与自动重排

触发空间或功率不足，Agent 提出调整隔板、替换候选机柜或迁移现有服务器的方案；确认后容量重新计算，受影响机柜同步更新。

### 9.3 链路查询

选择一台服务器，高亮其已知电力和网络链路，查看关联端口、设备、告警和变更记录；资料缺失处显示未知。

### 9.4 设备变更

发起迁移或隔板调整，查看前后对比与冲突检查，最终确认后执行并验证新位置。

### 9.5 报警诊断与恢复

通过演示场景触发功率过高、上架冲突或采集器离线告警；Agent 关联容量和拓扑生成诊断与修复方案；确认后执行修复，规则复核通过后告警转为已恢复。

### 9.6 服务异常与降级

模拟模型或采集器不可用，系统产生健康告警。模型失败时切换结构化表单和确定性规则；采集器失败时保留最后采集时间并使用设计容量。服务恢复后重新执行健康检查并关闭告警。

### 9.7 演示重置

管理员可将 JSON 状态恢复为固定种子数据。重置动作需要明确确认，并记录为管理操作，使每次演示都可以重复完整流程。

## 10. 异常处理

- 模型超时、网络失败或返回无效结构时，不生成伪造的 Agent 结果，自动提示使用结构化表单和本地规则引擎。
- 方案确认前若库存或容量版本变化，原方案失效并要求重新计算。
- 模拟执行采用执行前快照；部分步骤失败时恢复快照并生成失败告警。
- 实时采集未接入或过期时显示状态和最后采集时间，容量判断继续使用设计上限。
- 链路字段缺失时返回部分结果和未知节点，不补造连接。
- 硬约束失败返回结构化阻断原因，前端禁用最终确认。
- 并发修改同一机柜时只允许第一个持有有效资源锁的执行继续。

## 11. 私有模型集成与安全

私有模型通过兼容 OpenAI `/v1/chat/completions` 的服务接入，配置仅来自服务器环境变量：

- `AGENT_BASE_URL`
- `AGENT_API_KEY`
- `AGENT_MODEL`

API Key 不写入代码、JSON、前端、日志、规格文档或 Git。由于密钥曾在图片中展示，服务器部署前必须轮换。

远程演示版使用登录保护和服务器端会话。角色最少包括只读查看者和管理员：查看者只能浏览与查询，管理员可以发起并确认模拟变更、触发演示场景和重置数据。生产方向预留规划人与审批人分离，但 V0.2 不实现复杂组织权限。

部署入口使用 HTTPS 和反向代理；应用不直接把模型服务地址或密钥暴露给浏览器。日志对请求头、密钥和敏感字段进行脱敏。

## 12. 测试策略

- 单元测试：机柜功率映射、42U 分层、2U 层预留、10U 服务器位置、排序、容量、重量、端口和硬约束阻断。
- Agent 边界测试：验证模型输出模式、允许的调整范围、调整后复核和模型失败降级。
- 集成测试：库存读取、方案状态机、资源版本检查、快照恢复、告警状态机和审计关联。
- API 测试：输入校验、鉴权、错误响应、只读与变更权限、密钥不泄漏。
- 浏览器闭环测试：上架、重排、链路查询、变更、报警诊断、服务降级和演示重置。
- 回归测试：保留现有测试并为修正后的 42U/功率规则增加覆盖。
- 验收前执行秘密扫描，确认仓库、静态资源和日志中没有模型密钥。

## 13. 部署设计

- V0.2 打包为单个 Docker 应用，挂载持久化 JSON 数据目录和环境变量。
- 服务器前置 Nginx 或等价反向代理，提供 HTTPS、域名和访问控制。
- 提供健康检查，分别报告 Web、JSON 存储、模型服务和遥测适配器状态。
- 演示环境使用固定种子数据，可从 UI 恢复；生产环境禁用演示告警触发和一键重置。
- 后续迁移到 NetBox 时，仅替换 `InventoryRepository`；接入 PDU 和监控时，仅增加 `TelemetryProvider` 实现；真实执行通过新的 `ExecutionAdapter` 接入。

## 14. V0.2 验收标准

- 22 个机柜、设计功率映射、42U 四层结构和服务器详情正确展示。
- 每层只预留一次 2U，10U 服务器只能进入 L01，Agent 能推荐可移动隔板位置。
- 功率判断以服务器机柜 10/20 kW 设计上限为准，并明确实时功率尚未接入。
- Agent 的任何调整都能查看原因，且调整结果通过确定性规则复核。
- 硬约束失败不能进入最终确认。
- 所有状态变更只有一次最终确认，确认后重新检查版本、执行并验证。
- 上架、容量重排、链路查询、设备变更、报警诊断、服务降级和数据重置场景均能在 UI 中完成闭环。
- 机柜、服务器、链路、告警和审计记录之间能够相互跳转。
- 模型不可用时系统仍可用结构化表单和规则引擎完成核心演示。
- 应用可通过受保护的 HTTPS 网站远程访问，代码和前端中不存在模型密钥。
