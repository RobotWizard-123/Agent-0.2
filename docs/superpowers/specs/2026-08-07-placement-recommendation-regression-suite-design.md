# 推荐上架增量回归测试集设计

## 1. 目标

为推荐上架功能建立可直接运行的结构化自动化测试集，覆盖核心规划引擎、兼容推荐接口和浏览器 UI。测试集以追加方式维护：Bug 出现后先追加可复现该 Bug 的回归用例，再修复业务代码；既有用例不删除、不原地改写。

测试集首版收录现有推荐和 UI 上架场景作为基线，并加入经用户审核通过的真实场景。此后由 Codex 提出的真实场景必须先经过用户审核，获得确认后才能写入用例集。

## 2. 已确认的维护原则

- 所有用例均可直接运行，不以纯文档清单代替自动化验证。
- 覆盖 `createPlanningEngine().recommend()`、`recommendPlacement()` 和浏览器 UI 上架流程。
- Bug 回归用例必须关联稳定的 `bug_id`；外部工单链接可选。
- 基线用例使用 `BASE-REC-*` 编号。
- Bug 用例使用 `BUG-<工单号>-*` 编号。
- 经审核的真实场景使用 `SCENARIO-REC-*` 编号。
- 正式登记到统一 `cases.js` 后，测试集只追加用例，不删除或原地改写既有用例。
- 弃用用例保留原始代码，只追加 `despair` 生命周期记录；运行时显示为跳过。
- 内容有误的旧用例同样不原地改写：先追加 `despair`，再追加带 `supersedes` 的替代用例。
- 统一登记前已经存在、依赖旧演示库存的浏览器用例允许进行一次适配性重设计：保留原业务验证目的，在全空启动状态下通过 UI 自行建立前置数据；这些用例不因 fixture 改变而标记 `despair`。

## 3. 架构

采用“统一场景源 + 分层执行器”结构。新增目录 `tests/placement-recommendation/`：

- `cases.js`：统一、只追加的结构化场景定义。
- `fixtures.js`：构造机柜容量、占位、功率、重量和网络端口等测试状态。
- `core.test.js`：执行核心规划引擎场景。
- `compatibility.test.js`：执行兼容推荐接口场景。
- `lifecycle.js`：只追加生命周期记录，包括 `despair`。
- `case-schema.test.js`：验证用例与生命周期数据的治理规则。

不新增独立 Playwright 文件。现有 `tests/e2e/closed-loops.spec.js` 导入同一 `cases.js`，以增量注册循环运行包含 `ui` level 的用例；文件中原有闭环用例继续保留，并按全空启动状态重设计其前置步骤。

统一入口保留在同一文件夹内：

- `run-test-set.js`：按 `core`、`ui` 或 `all` 模式组织命令并传递退出码。
- `run-test-set.cmd`：Windows 双击和命令行入口，交互运行结束后暂停，自动化运行可使用 `--no-pause`。

因此，结构化场景、治理测试和执行脚本集中在一个测试集目录内，而浏览器交互复用项目已有的闭环测试文件和 E2E 启动栈。

## 4. 用例模型

结构化用例采用 JavaScript ESM 对象，以便 Node.js 测试和 Playwright 直接导入，同时允许 fixture 构建器生成复杂领域状态。

```js
{
  id: "BUG-DC-1427-01",
  title: "功率不足时不得推荐目标机柜",
  origin: {
    type: "bug",
    bug_id: "DC-1427",
    reported_at: "2026-08-07"
  },
  levels: ["core", "compatibility", "ui"],
  tags: ["power", "hard-constraint"],
  fixture: "power-constrained-rack",
  request: {},
  expected: {
    core: {},
    compatibility: {},
    ui: {}
  }
}
```

`origin.type` 允许 `baseline`、`bug` 和 `real-world`。`bug` 类型必须提供 `bug_id`；`real-world` 类型必须记录 `approved_at`。URL 只用于追溯，不参与执行。

`levels` 允许 `core`、`compatibility` 和 `ui`。每个 level 必须有对应断言。用例可以只覆盖适合自己的层级，不能为了形式统一而给浏览器增加生产测试后门。

## 5. 生命周期与 `despair`

`lifecycle.js` 以追加记录的方式给用例派生生命周期标签。记录至少包含：

```js
{
  case_id: "BASE-REC-003",
  tag: "despair",
  reason: "需求已被新硬件规范替代",
  recorded_at: "2026-08-07",
  superseded_by: "SCENARIO-REC-009"
}
```

原始用例内容保持不变。执行器读取生命周期记录后，为用例附加 `[despair]`，并调用测试框架的 skip 能力。测试报告仍显示用例编号与弃用原因，但该用例默认不执行，也不计作通过。

只有显式 `despair` 允许跳过。fixture 缺失、字段非法、执行器不支持断言等情况必须失败。

## 6. 执行方式

统一测试集直接通过文件夹内脚本运行：

```powershell
tests\placement-recommendation\run-test-set.cmd core
tests\placement-recommendation\run-test-set.cmd ui
tests\placement-recommendation\run-test-set.cmd all
```

文件夹内的 Windows `.cmd` 入口默认在执行完成后显示退出码并等待按键，便于双击运行时查看结果。CI 或其他无人值守调用在模式前传入 `--no-pause`，例如 `run-test-set.cmd --no-pause ui`。

- `core` 运行 schema、核心和兼容接口用例。
- `ui` 使用现有 E2E 栈和 `closed-loops.spec.js` 运行结构化 UI 用例。
- `all` 顺序运行以上两组，任一组失败即返回非零退出码。

UI 用例沿用现有固定端口、管理员登录、单 worker 和每例重置演示数据的机制。测试只通过真实页面和公开接口构造状态。Playwright 继续在失败时保留 trace 和截图。

## 7. 断言规则

每个用例必须声明可诊断的业务结果，不能只检查“存在候选”：

- 成功推荐校验允许状态、机柜、层位、起始 U 位、设备数量、约束余量和求解器来源。
- 无法推荐校验候选为空，并校验稳定拒绝码。
- 排序场景校验首选候选和关键排序依据，不使用完整对象快照。
- 兼容接口额外校验旧输入字段映射和兼容输出结构。
- UI 校验用户可见的机柜、U 位、约束说明、策略和求解器状态。
- 完整闭环 UI 场景在最终确认后校验库存结果。
- 确定性场景对相同 fixture 和请求重复执行，校验候选顺序、首选机柜和关键评分稳定。

测试名称包含用例 ID、执行层级和标签，使 CI 失败可直接追溯到场景或 Bug。

## 8. 自动治理

`case-schema.test.js` 拒绝以下情况：

- 用例编号重复；
- Bug 用例缺少 `bug_id`；
- 真实场景缺少审核时间；
- 使用未知 level、fixture 或受控标签；
- 声明 level 却缺少对应断言；
- `despair` 指向不存在的用例；
- 同一用例重复追加相同生命周期状态；
- `supersedes` 或 `superseded_by` 指向不存在的用例；
- UI 用例缺少用户可见断言。

跨提交的“不可修改、不可删除”由维护流程和代码审查保证；测试集内部通过稳定编号、替代关系与追加式生命周期保存完整历史。首版不引入依赖 Git 历史的自定义差异解析器。

## 9. Bug 增量流程

1. 获取稳定 Bug 编号。
2. 向 `cases.js` 追加一个最小复现场景，并声明实际受影响的 levels。
3. 运行聚焦用例，确认它因该 Bug 失败，而非因测试配置错误失败。
4. 修复业务代码。
5. 运行聚焦用例、推荐测试全集和项目原有测试。
6. 保留新增用例作为永久回归证据。

生产代码修复遵循 red-green-refactor；没有先看到回归用例按预期失败，不修改业务实现。

## 10. 首版基线

从现有测试提炼以下能力作为 `BASE-REC-*` 基线：

- 普通 4U 设备生成合法、带证据的推荐。
- 合法优选机柜排在首位。
- 10U 设备只能进入 L01。
- 超过单层容量的设备被拒绝。
- 固定层无法容纳时才考虑隔板调整。
- 直接上架无解时生成带 warning 风险的迁移备选。
- 副本批次跨电源域和交换机域分散。
- 三种部署策略暴露正确策略 ID 并保持稳定排序。
- CP-SAT 成功、不可行与不可用回退语义。
- 兼容输入字段正确映射到新规划模型。
- UI 展示策略、精确 U 位、求解器证据，并完成一次最终确认和库存验证。

## 13. 网站全空启动状态

网站每次启动都强制恢复全空库存，不保留上一次运行的业务数据。服务必须在开放 HTTP 端口前完成恢复，避免用户看到旧库存或恢复过程中的中间状态。

每次启动和“重置演示数据”均清空：

- 服务器设备及 U 位占用；
- 设备功率连接和网络连接；
- 部署方案、告警、诊断、变更记录和审计记录；
- 运行期间产生的演示条件。

以下基础设施与配置继续保留：

- 22 个机柜及其 42U 分层、每层预留空间和容量上限；
- 配电源、PDU、接入交换机、核心交换机和机柜之间的设计拓扑；
- 用户认证配置和默认部署策略。

实现上保留现有混合占用状态生成器供明确需要复杂 fixture 的核心测试使用；新增全空状态生成器作为网站 seed。服务启动后无条件以该 seed 覆盖 runtime 状态，因此重启会有意丢弃上次部署数据。

全空启动也改变了规划器的必要起步语义：

- `consolidated` 在不存在已启用服务器机柜时，必须允许选择一个合法空机柜作为首个集中目标；不能因为“会启用空机柜”而让全空机房永远无候选。
- 批量请求中的优选机柜应持续接收仍满足硬约束的设备，达到任一容量边界后再安全溢出，不能只对批次第一台应用优选倾向。
- 批量生成器遇到单机柜 U 位、功率、重量或端口不足时，应继续搜索其他合法机柜；只有整个机房无法容纳完整批次时才原子拒绝。
- 原子语义保持不变：成功候选必须包含完整 `count` 条部署动作，失败结果不得包含可执行的部分批次。

这些行为通过 `SCENARIO-REC-010`、`013`、`014`、`019`、`020` 和 `021` 形成浏览器回归，并在核心层补充最小算法用例。当前实现若不能满足上述行为，实施时按 red-green-refactor 修正规划器，而不是放宽场景断言。

## 14. 依赖旧库存的 UI 用例重设计

这些用例仍验证有效业务能力，不追加 `despair`，而是在全空状态下自行建立前置数据：

- **机房总览与设备详情**：先断言 22 个机柜均为空，再通过 UI 上架一台设备；进入实际分配机柜检查服务器详情、PDU 和网络链路。
- **设备取出闭环**：先通过 UI 上架一台可取出设备，再执行取出、最终确认、库存 404 和审计验证。
- **拓扑查询与行政重置**：先通过 UI 上架设备并查询其电力和网络证据；重置后验证设备、占用和连接全部消失，22 个机柜恢复空闲。
- **机柜容量风险颜色**：先向指定机柜部署接近预警线的高功率设备，再验证总览颜色、风险依据和容量百分比。
- **审计详情**：由用例自身完成一次可审计操作后再检查详情，不依赖 seed 中预置审计。

告警处置、执行失败回滚和只读用户权限等本来不依赖预置设备的用例保持原业务流程，只把起点统一为全空 reset。

核心测试新增启动恢复断言：即使 runtime 中预先存在设备、连接和业务记录，执行网站启动初始化后也必须恢复全空 seed。浏览器测试负责验证用户首次看到的是全空机房；核心测试负责验证重启覆盖语义，避免在 Playwright 内部重启被测服务。

## 15. 完成标准

- 三类执行器可以从同一场景源运行各自声明的用例。
- 所有首版基线和已审核真实场景已结构化登记。
- `despair` 用例保留并在报告中显示为跳过。
- schema 治理测试覆盖编号、Bug 追溯、审核、层级、fixture、断言和生命周期关系。
